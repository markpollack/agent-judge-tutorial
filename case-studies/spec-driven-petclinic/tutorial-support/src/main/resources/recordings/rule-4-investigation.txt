The inversion only matters if some other transaction acquires the same two rows in the mandated order concurrently. It does, from three independent directions, all on the *same* `owners` and `scheduling_requests` rows:

1. The lifecycle sweeper. `LifecycleScheduler` is enabled by default (`matchIfMissing = true`) and fires every 5000 ms by default. Its `processOverdueFallback` selects requests whose status is `STAFF_QUEUED`/`STAFF_OFFERED` with an elapsed `fallbackDeadline` — precisely the population the staff queue UI works on — and locks Owner→Pet→Vet→Request in one `lockResources` call. `processOverdueStaffOffer` does the same for expired `STAFF_OFFER` reservations, which are the rows `createStaffOffer` itself creates. Note that `createStaffOffer` clamps `expiresAt` down to `fallbackDeadline` (`StaffFallbackService.java:283`), so an offer written at or past the deadline is born already expired and is picked up by the very next sweeper tick — the window is ≤5 s, not rare.

2. Owner-facing reservation actions. `ReservationService.acceptGuidedHold` / `rejectGuidedHold` / `commitGuidedHold` lock Owner-first. Their pre-lock guards (only `CONFIRMED` short-circuits `accept`, only `REJECTED` short-circuits `reject`) do not exclude a request sitting in staff fallback, so a stale owner submit still reaches `lockResources` and contends.

3. `RetentionService.purgeOverdueRequest`, also driven by the same sweeper, is likewise Owner-first.

Crucially the status guards cannot prevent this: in every counterparty the authoritative status re-check happens *after* the locks are taken (e.g. `LifecycleProcessor.java:169-173`), and in `createStaffOffer` there is no status check at all. So mutually exclusive states do not narrow the window — both transactions still race through lock acquisition first.

Blast radius is bounded: the transaction rolls back cleanly, so there is no torn write or lost update, and `LifecycleProcessor` catches per-item exceptions and retries on the next tick.
